# Split inventory: physical store vs. online shop — Plan & Work In Progress

Today there is one inventory; this splits it into two stock pools, one for the **physical store**
and one for the **online shop**. Tracked as `PLAN.md` § 11.

Status: **NOT STARTED** — plan only, not yet approved for implementation.

## Current state

- One Postgres table `products` (`ProductEntity`: `name`, `type`, `availableAmount`, unique on
  `name`+`type`), schema generated by Hibernate (`drop-and-create`, no migrations).
- `InventoryRepositorySPI` (`addAmount`, `deductAll`, `findAll`), implemented by
  `outbound-postgres` `InventoryService`.
- Both sales channels deduct from the same pool, differing only in `OnShortage`:
  - `PurchaseHandler.checkout` (online: `ShopReceiver`, `ProductApiReceiver`) — `REJECT`, 409.
  - `PurchaseHandler.recordStoreSale` (store: Kafka `CashpointReceiver`) — `CAP_AT_ZERO` + audit
    `STOCK_DISCREPANCY`.
- All deliveries (`InventoryHandler.updateXxxAmount`, Kafka `*DeliveryReceiver`s) add to that pool.
- Readers: `ProductsHandler.listAll()` → `/admin` inventory table, `/shop` (in-stock filter),
  `GET /api/products`.

## Target shape (first sketch)

- A core concept for the location, e.g. `enum StockLocation { STORE, ONLINE }`.
- `InventoryRepositorySPI` methods take the location; `checkout` deducts from `ONLINE`,
  `recordStoreSale` from `STORE` — the `OnShortage` split stays as it is and now lines up with the
  location.
- `/shop` and its future live stream (§ 10) show only `ONLINE` stock; `/admin` shows both.
- Audit entries name the location.

## Steps

1. Decide the open questions below.
2. Core: `StockLocation`, SPI signatures, `InventoryHandler`/`PurchaseHandler`/`ProductsHandler`.
3. `outbound-postgres`: persistence per the decision below.
4. Inbound adapters: deliveries (Kafka), admin orders, shop, cashpoint, JSON API.

## Open questions / decisions needed

- **Where do deliveries go?** Supplier deliveries arrive on Kafka without a destination. Options:
  (a) the delivery message carries a location, set by the admin order form (order *for* the store
  or *for* online); (b) everything is delivered to one pool (e.g. `STORE` as the warehouse) and
  moved by transfers; (c) a fixed split rule. This drives most of the change.
- **Transfers between the two pools** — needed (admin form "move N apples store → online")? Only
  required if (b) above.
- **Persistence**: one table with a `location` column (unique on `name`+`type`+`location`) vs. two
  tables. Recommendation: one table + column — the locking/`deductAll` code stays shared.
- **JSON API**: `GET /api/products` — which pool? `ONLINE` only (it is an online channel, like
  `/shop`), both with a location field, or a `?location=` parameter. `POST /api/products/purchase`
  → `ONLINE`.
- **Naming** — "store" vs. "physical store", "online" vs. "webshop"; worth an entry in the domain
  glossary if one exists.
- **Interaction with § 10**: the shop's data island only carries `ONLINE` amounts; the admin island
  carries both. Order doesn't matter much, but whichever lands second adapts to the other.
